# Decisions

Choices made during the build. Later sessions must not change these without asking.
At the end of every phase, the agent appends its rulings here under a new heading.

## Phase 3 — storefront catalog
- FTS rows use `rowid = product.id`: one row per product, with active SKUs aggregated.
- Admin search uses FTS5 over all statuses and the slug; the storefront search adds `status = 'active'`. No `LIKE '%q%'` anywhere.
- Category filtering covers the selected category plus its direct children only.
- Keyset cursors are base64url JSON (`{id}` or `{price,id}`). No OFFSET.
- Product cards show "From" the cheapest active variant. The detail page defaults to that variant, and JSON-LD uses its price and SKU.
- Stock labels, stock state, and JSON-LD availability honour `product.track_stock` and `config.features.stockTracking`.
- Locale order: `?lang=`, then the locale cookie, then config.
- `theme.preset` is config-driven. Radius and font values are validated to block CSS injection.
- Section, social, and logo URLs reject `javascript:`, protocol-relative, and `/\` paths.
- Homes without a hero get a hidden H1. Only the first hero renders an H1.
- No external fonts or JS framework on the storefront: SSR plus small inline scripts.
- Query budgets: home 4, shop 3, product 4.
- Server-side re-pricing is Phase 4's job. The product page only shows the selected variant's price.

## Phase 4 — cart, checkout, COD orders
- Prices, line totals, shipping, and order totals are always recomputed from D1. The client supplies only product id, variant id, and quantity; price/total fields are stripped by Zod and ignored. An unsafe (non-safe-integer) line total marks the line unavailable, and admin prices are capped at 1,000,000,000 BDT.
- A line uses `variant.price` when it is not null, otherwise the product price. Out-of-stock, inactive, missing, and variant-required lines are marked unavailable and block order creation.
- Delivery zone is derived from the district: Dhaka district → `dhaka`, every other district → `outside`, with the first/last configured zone as a fallback. `freeShippingOver` is applied server-side. There is no client-supplied shipping fee.
- COD is the only accepted payment method in Phase 4; bKash/Nagad and coupons are deferred.
- Products with no variants, and products with `track_stock = 0`, are orderable without stock checks or decrements. Tracked variants require a variant id and use the selected variant's stock.
- One `db.batch` contains the stock update, guard, order, items, and event rows. The stock update is a single `UPDATE ... WHERE stock >= qty` fed by one JSON parameter (`json_each`), so a 50-line cart stays under D1's 100-bound-parameter limit. A one-row `checkout_guard` CHECK compares `changes()` with the expected tracked-line count, so D1 rolls back the whole order if any line was short. Measured on real local D1: 50 concurrent orders for stock 5 produced exactly 5 orders, stock 0, and 45 409s; a 30-line order succeeded.
- Every checkout requires `idempotency_key`. The route checks it before pricing; a repeat returns the same order (200) without pricing or writing. `orders.request_hash` stores a SHA-256 fingerprint of the customer, geo, items, and payment method: a repeated key with a different intent gets 409 instead of silently returning the old delivery details. A concurrent UNIQUE race re-reads the winner and returns it when the intent matches. The client keeps one key per cart signature and rotates it when the cart, phone, or address changes.
- `order_items` snapshots the localized product title and the variant title with its options. `variant_id` and `product_id` stay as references for admin views.
- Turnstile runs only when both keys are configured. An invalid/missing token fails the checkout; Siteverify 5xx/429/network errors and `internal-error` responses fail open with a warning, while 4xx configuration errors and `bad-request` fail closed and log loudly. `.dev.vars.example` lists Cloudflare's official test keys in comments; no test keys are hardcoded in application code.
- `src/data/bd-geo.json` comes from the MIT `nuhil/bangladesh-geocode` dataset (8 divisions, 64 districts, 495 upazilas). The checker validates the full hierarchy server-side; the generator is `scripts/generate-bd-geo.mjs`.
- `/order/[number]` and `/track` require order number + phone, are read-only, send `Cache-Control: no-store`, and are `noindex`. `/track` uses POST. The checkout island submits the confirmation as a one-time POST form, so the phone number never enters the URL or browser history.
- If D1 fails during order creation, the API returns a 503 with a prefilled fallback message and configured Messenger/WhatsApp/tel links; it never returns a raw error. Cart/checkout/order/track pages fall back to the default config when the settings read fails, and order/track show a friendly unavailable card instead of a raw 500.
- D1 errors are classified before the outage heuristic: constraint failures (`UNIQUE`, `CHECK`) are not treated as outages, so idempotent retries return the existing order and guard failures return out-of-stock. A rare `orders.number` UNIQUE collision retries up to 4 times with a fresh number inside the same service; the failed batch rolls back.
- Query counts (dev instrumentation, D1 round trips): checkout 4 for a new order and 2 for an idempotent retry; cart price 2; cart and checkout pages 1; order and track pages 3.
- Supersedes the Phase 3 "no JS framework on the storefront" ruling: the mini-cart, add-to-cart, cart page, and checkout use small Preact islands; catalog pages still ship only their small inline scripts.
- The client stores one idempotency key per cart signature. Retrying an unchanged cart reuses the key; changing the cart rotates it, so a lost response cannot make the client clear a new cart while returning an old order.
- Physical browser pass at 390 px: the header search moves to a full-width second row, and the confirmation page deduplicates locality names already present in the street address (for example "House 12, Road 5, Savar" + upazila Savar).

## Phase 5 — admin orders and dashboard
- Asia/Dhaka is treated as a fixed UTC+6 offset (no DST). Date filters are half-open UTC ranges for one Dhaka calendar day; the dashboard uses the Dhaka day containing “now”.
- The dashboard week starts Saturday 00:00 Asia/Dhaka. “This week’s revenue” is the sum of order totals placed in that window, excluding `cancelled`, `returned`, and `payment_status = 'refunded'`. It is a placed-order figure, not cash collected.
- The orders list filters by exact normalized phone, status, and Dhaka date range. A partial phone or invalid date/range shows a clear filter error; it is not silently ignored.
- Keyset pagination is `(created_at, id) < (?, ?)` ordered by `created_at DESC, id DESC`. The first page uses a far-future cursor so `EXPLAIN QUERY PLAN` reports an index `SEARCH`, not a whole-index `SCAN`. Cursors are base64url JSON `{t,i}` and invalid/tampered cursors restart at the newest page.
- The list pins the matching composite index with `INDEXED BY`: `(created_at,id)`, `(status,created_at,id)`, `(phone,created_at,id)`, or `(phone,status,created_at,id)`. All filter/cursor combinations in the tests show `SEARCH ... USING INDEX` with no `SCAN` and no temp B-tree.
- The older `idx_orders_status` / `idx_orders_phone` indexes are retained to avoid a destructive migration. The keyset indexes add per-order index writes; removing the old pair is a later optimisation.
- Allowed transitions are exactly `pending→confirmed→shipped→delivered`, cancel from `pending`/`confirmed`, and return from `shipped`/`delivered`. Everything else returns 409 with the current status.
- A status change is one batch: optimistic `UPDATE ... WHERE id = ? AND status = ?`, a one-row `order_transition_guard` CHECK on `changes() = 1`, the optional stock restore, and the `order_events` row. A lost race aborts and rolls back the whole batch, returning `status_conflict`; it cannot apply the transition or restore stock twice.
- Event `type` is the target status (`confirmed`, `shipped`, …); the optional admin note is the event message. The timeline reads `order_events` and stored order/item snapshots.
- `order_items.stock_tracked` records what checkout actually decremented (`line.track_stock && variant_id != null`). Cancel/return restores `SUM(qty)` once per variant only for `stock_tracked = 1` lines, independent of later product/config changes. Existing rows are backfilled best-effort from current `products.track_stock`; deleted products/variants cannot be restored.
- COD orders become `payment_status = 'paid'` when delivered. Cancelling or returning a paid order moves it to `refunded`; unpaid or pending-verification orders keep their payment status. Phase 6 owns payment verification/refund tooling.
- Invoices and packing slips are read-only and built only from `orders` and `order_items` snapshots. They never join current products/variants; `site.config.ts`/settings supply only shop identity, contact, and currency. Both pages accept `?lang=bn|en`.
- “Block this phone” writes `blocklist` with an upsert and shows the blocked state on the order. Checkout enforcement remains Phase 7.
- Page-body D1 round trips: dashboard 2 (one 5-statement KPI batch + config), orders list 2 (list + config), order detail 2 (one 4-statement detail batch + config), invoice/packing slip 2 (one print batch + config). The admin auth middleware adds one settings read, for 3 total.
- The dashboard shows all matching low-stock tracked variants (`track_stock = 1`, active product/variant, stock ≤ 5) as a count, with at most 10 rows listed. The count query is indexed.
- `admin.dashboard` stays a translated string for the nav/title; dashboard card keys live under `admin.dashboardCards.*`.
- No new dependencies. Admin pages and APIs remain behind the existing auth middleware, and no GET path writes D1.

## Phase 6 — manual payments, coupons, settings, presets
- Checkout accepts `cod`, `bkash`, and `nagad`. Wallet methods require a valid sender mobile number and a 6–32 character alphanumeric TrxID; both are normalized before storage. Wallet orders are created as `pending_verification`, COD stays `unpaid`.
- Manual payment verification is `POST /api/admin/orders/:id/payment` with `verify` or `reject`. Verify is allowed only from `pending_verification` (→ `paid`), reject from `pending_verification` (→ `unpaid`) or `paid` (→ `refunded`). Cancelled/returned orders and COD orders cannot be verified. Each successful action writes `payment_verified`, `payment_rejected`, or `payment_refunded` to `order_events`.
- Payment changes use one optimistic `UPDATE` (`WHERE payment_status = ? AND payment_method IN ('bkash','nagad') AND status NOT IN ('cancelled','returned')`), the existing `order_transition_guard` one-row CHECK, and the audit event in one batch. Two admins cannot apply the same payment decision or write two events.
- COD keeps the Phase 5 rules: delivered → paid; paid cancel/return → refunded. A wallet payment left `pending_verification` on cancel/return keeps that status, matching the Phase 5 ruling.
- Coupon discount is `round(subtotal × percent / 100)` or the fixed value, capped at the subtotal. Shipping is derived from the pre-discount subtotal; total = `subtotal − discount + shipping`. Money stays integer BDT.
- Coupon window is `starts_at <= now < ends_at` (half-open). Inactive, not-yet-started, expired, below-minimum, exhausted, missing, and malformed configurations return distinct `coupon_*` error codes. `POST /api/coupons/check` re-prices the server cart and returns the same codes.
- Coupon lookup is part of the existing item-pricing batch, so checkout with or without a coupon stays at 4 D1 round trips (2 for an idempotent retry). `coupon-check` costs 2.
- Coupon usage is incremented in the same D1 batch as the order, stock decrement, and item inserts. The `UPDATE` re-checks active/date/min/max and a one-row `coupon_guard` CHECK aborts the batch when it matched nothing. Concurrent checkouts cannot exceed `max_uses`; a failed guard also rolls back stock and the order. When the guard fails, the service first re-reads the `idempotency_key`; if a concurrent double-tap already created that order with the last coupon use, it returns the existing order instead of a false `coupon_unavailable`. Otherwise the route re-prices the cart to report the real coupon reason. Usage is counted when an order is placed and is not released on cancel/return (backlog).
- `features.coupons` is honoured server-side and by the checkout UI. The coupon admin page supports create, active toggle, and delete; editing a coupon is not implemented.
- Settings editors persist only top-level config sections as JSON rows (`name`, `tagline`, `logo`, `theme`, `shipping`, `payments`, `social`, `contact`). `home_sections` remains its own row. `loadConfigFromRows` still validates each row against `site.config.ts`; invalid/unknown rows are ignored. An enabled wallet must have a non-empty number.
- Homepage sections are validated per entry. One invalid section is dropped instead of resetting the whole layout; an unusable/empty list falls back to the default layout.
- The first-run wizard lives at `/admin/setup`. `/admin` redirects there only when `setup_completed` is absent and the catalog has no products or categories; otherwise it shows a setup card. Setup writes business/contact/shipping/payment/theme settings, the first category, and `setup_completed` in one batch.
- Logos are resized to a 400 px WebP in the browser, uploaded to R2 under `brand/…`, and served through `/img/brand/…` or `R2_PUBLIC_URL`. The previous brand object is deleted after the new settings row commits. The storefront header renders the configured logo.
- Business presets live in `src/presets/` and are applied by `POST /api/admin/presets/apply`. They are add-only: categories use `INSERT OR IGNORE` by slug; products use `INSERT OR IGNORE` by slug; variants are inserted only for products created by this apply (never added to an existing owner product). FTS rows are refreshed. Applying a preset writes no extra settings row, so it cannot overwrite owner data. Re-applying adds nothing.
- Page/query counts: admin dashboard body 2 (first-run 3) + 1 auth; order detail 2 + 1 auth; settings 1 + 1 auth; setup 1 + 1 auth; coupons 2 + 1 auth. The new coupon lookup and payment lookup use primary-key indexes (`SEARCH coupons USING INDEX sqlite_autoindex_coupons_1`, `SEARCH orders USING INTEGER PRIMARY KEY`).
- No new dependencies. New admin pages/APIs stay behind the existing `/admin` middleware. No GET path writes D1; the new pages are covered by the no-GET-writes test.

## Phase 7 — courier integration and fraud controls
- Phase 7 is scoped to courier integration plus fraud controls only. The other six Phase 7 backlog items (delivery-zone editing, coupon editing, wallet re-verify, inventory restore gaps, paid-only revenue metric, transition note field) are retagged to Phase 8 in `doc/BACKLOG.md`.
- The `Courier` interface is `createParcel(input)` + `getStatus(consignmentId)`. Only a Steadfast adapter exists. `getCourier(env)` returns `null` unless both `STEADFAST_API_KEY` and `STEADFAST_SECRET_KEY` are set, and the admin order page only renders `CourierPanel` when both are present, so the courier UI is entirely hidden without credentials.
- Steadfast endpoint facts were taken from the community-hosted API document plus live endpoint probes, because Steadfast does not publish a clearly-hosted official docs URL. Base URL `https://portal.packzy.com/api/v1`; headers `Api-Key`, `Secret-Key`, `Content-Type: application/json`; `POST /create_order` (body `invoice`, `recipient_name`, `recipient_phone`, `recipient_address`, `cod_amount`, optional `note`, `item_description`, `total_lot`) returns `{ status: 200, consignment: { consignment_id, tracking_code, status, … } }`; `GET /status_by_cid/{consignment_id}` returns `{ status: 200, delivery_status }`. `delivery_type` is omitted because its value set is unclear. HTTP 401→`auth`, 422→`rejected`, 429→`rate_limited`, 5xx→`unavailable`; every call has an 8 s `AbortController` timeout (`timeout`); a malformed body maps to `invalid_response`.
- Courier calls run only on an explicit admin POST (`POST /api/admin/orders/:id/courier` with `send` or `refresh`); page rendering never calls the courier, so a slow or down courier cannot block admin pages.
- Only a `confirmed` order without a `consignment_id` can be sent. Sending first wins a 2-minute claim token (`courier_claim`/`courier_claimed_at`) in one batch; a concurrent click or a second admin sees `in_progress`, and a stale claim can be retried. The final write is guarded by the same claim. A courier error releases the claim. Refresh updates `courier_status`/`courier_status_updated_at` only; it never changes the order status and does not move the customer-visible `updated_at`. Courier error codes map to 400/404/409/422/429/502/504 with `courier_*` admin messages.
- Courier sending is at-most-once per invoice, not blindly at-least-once. Steadfast keys parcels by the unique `invoice` (= `order.number`), so a 422 that names the invoice as duplicate/already-existing maps to `duplicate_invoice` → admin `courier_duplicate`: the parcel is not re-POSTed, the claim is released, and the admin is told to reconcile in the Steadfast portal. This closes the window where `create_order` succeeded but the D1 write or JSON parse failed: the safe retry returns `courier_duplicate` instead of creating a second parcel. There is no Steadfast lookup-by-invoice endpoint, so a parcel created and then lost to a D1 failure must be reconciled by hand.
- Fraud config lives in `site.config.ts`/settings under `fraud`: `enabled` (default true), `orderLimitPerPhone24h` (5), `orderLimitPerIp24h` (50), `advancePaymentForFlaggedPhones` (true). The blocklist always applies; `enabled` gates the rate limits and the advance-payment rule. The per-IP default was raised from 20 to 50 during the Phase 7 merge because Bangladeshi mobile carriers put many customers behind one CGNAT address.
- Checkout runs a best-effort in-isolate in-memory limiter (30/min per IP, no D1 round trip) before the D1 batch, then reads settings, the blocklist, the phone flag, the last-24 h per-phone order count, and an idempotent retry in one `db.batch`, then prices the cart, then creates the order. Turnstile verification stays after the batch so an idempotent retry still returns the existing order without burning a single-use token. The IP source is `cf-connecting-ip` only; when it is absent (local dev/tests) IP hashing and IP limiting are skipped, and when `fraud.enabled` is off no IP-derived value is hashed or stored. The per-install salt is seeded by migration `0011` via `hex(randomblob(32))` and stored in `settings`; `SHA-256(salt + ":" + ip)` is stored in `orders.ip_hash`, so raw IPs are never persisted or logged. Limits return 429 `order_rate_limited` with `Retry-After`; a blocked phone returns 403 `phone_blocked`; a flagged COD attempt returns 409 `advance_payment_required`.
- The blocklist page (`/admin/blocklist`) lists blocked and flagged phones and can add/unblock/clear-flag them through the existing admin routes (`GET/POST/DELETE /api/admin/blocklist`, `DELETE /api/admin/blocklist/flags/:phone`). Order-level flag toggling is `POST /api/admin/orders/:id/phone-flag`.
- Duplicate bKash/Nagad TrxIDs are prevented by `orders_duplicate_trx_insert`/`_update` triggers plus `idx_orders_payment_trx`, so two orders cannot share a TrxID. The order detail page still lists any pre-existing duplicates as a clear banner, and the checkout API also returns 409 `duplicate_payment_trx`.
- The coupon release supersedes the Phase 6 "not released on cancel/return" ruling: a cancelled or returned order runs `UPDATE coupons SET used = MAX(used - 1, 0)` in the same batch as the optimistic status change, so the exactly-once transition guard also guarantees the release happens once.
- Coupon checking and order tracking are limited in memory per isolate (20 coupon checks/min and 10 track attempts/min per IP) using salted FNV-1a map keys; there are no D1 writes, and the limiter is best-effort across isolates. The track limit applies to both `/api/track` and the `/track` page POST.
- Query/round-trip counts supersede Phase 6 where they differ: checkout 3 for a fresh order without an IP and 4 with one (context batch + IP count + pricing + create), 1 for an idempotent retry; the admin order detail batch grew to 6 statements (order, items, events, blocklist, phone flag, duplicate TrxID) but stays 2 page-body round trips; the blocklist page body is 2 (blocklist + flags) plus the 1 auth read. All new hot queries use indexes: `idx_orders_phone_created_id`, `idx_orders_ip_created`, `idx_orders_payment_trx`, the `blocklist`/`phone_flags` primary keys, and the orders primary key for courier claim/update/refresh. The Phase 7 index test prints every plan and fails on a `SCAN` or temp B-tree.
- The Phase 7 review of Turnstile/IP handling confirms `cf-connecting-ip` is the only request IP source for Turnstile `remoteip`, IP hashing, and the in-memory limiters; it is trusted only as set by Cloudflare, and no raw value is stored.
- The fraud defaults are `enabled: true`, 5/phone, 50/IP, advance payment on. The per-IP cap counts every order attempt in the window, including cancelled/returned, so it cannot be reset by cancelling; the trade-off is that Bangladeshi carrier CGNAT makes many customers share an IP, so owners who see false `order_rate_limited` errors should raise `orderLimitPerIp24h` further (or turn `fraud.enabled` off) in Settings. The settings hint states the 5/phone and 50/network defaults, that the limits use a rolling 24-hour window, and that the blocklist always applies.
- No new dependencies. New pages/APIs stay behind the existing `/admin` middleware, and no GET path writes D1 (the blocklist page is in the no-GET-writes test).

## Phase 8A — launch-critical
- bKash USSD dial link: `tel:*247%23` (the `#` is percent-encoded), rendered on mobile only (`sm:hidden`). Official source checked 2026-11-28: <https://www.bkash.com/en/products-services/payment> (bKash product page: “Dial *247#”). Nagad has **no** dial link: no official nagad.com.bd page documenting `*167#` could be found, so the code is not shown. Revisit if Nagad publishes an official USSD page.
- Wallet checkout now offers “Copy number” and “Copy amount” (Clipboard API, `document.execCommand('copy')` fallback), the bKash dial link, an optional per-wallet QR, personal-vs-merchant step lists, and a prominent “not confirmed until verified” notice. Copy amount copies the integer taka total currently shown by the server-priced summary.
- Payment QR images are owner uploads from Settings: PNG/JPEG/WebP magic-byte validation, 1 MB max, R2 key `payment-qr/{wallet}-{uuid}.{ext}`, served by `R2_PUBLIC_URL`/the image-address setting or `/img/*`. The `/img/*` route now returns the stored content type instead of always `image/webp`. Old QR objects are not deleted on replacement (orphan cleanup is backlog).
- Image address: new `images.address` settings row (default empty). Validation is https-only, no trailing slash, no query/hash, no credentials, no localhost/`.local`/`.internal`, and no private/loopback/link-local/CGNAT IPv4 or ULA/link-local IPv6. It is never fetched server-side. It takes priority over `R2_PUBLIC_URL` for product-image rendering and when new logo/QR URLs are created (already-stored absolute logo/QR URLs are not rewritten; backlog). The admin Worker banner is hidden only when either the setting or `R2_PUBLIC_URL` is present.
- Image-address “Test” runs only in the browser: it probes a stored object (first product thumb, else brand logo, else wallet QR) at `{address}/{key}` with an `<img>` and an 8 s timeout. A hanging or blocked host re-enables the button with a friendly failure. The GUI can only prove the failure path locally because the setting rejects localhost.
- Shipping config now has `shipping.districtZones` (district name → zone id, case-insensitive lookup) and `shipping.fallbackZone`. Every district resolves to the fallback when unmapped; an unknown runtime fallback falls back to the first zone. Zone ids must be unique and start with a letter/digit; legacy ids with capitals or spaces are accepted, and the fallback must be one of the zones. The Settings UI renders all 64 districts grouped by division and can add/remove zones; removing a zone remaps its districts to the fallback. Existing shops with only the old `{zones, freeShippingOver}` row keep working because deep-merge supplies `{Dhaka: 'dhaka'}` and `outside`; an old fork `site.config.ts` is normalized before parsing so it also keeps working (it gets `{Dhaka: 'dhaka'}` + `outside`, or the first/last zone for custom legacy ids, matching the pre-8A fee behavior). The upgrade is tested. Stored `orders.shipping_fee` is never recalculated.
- Dashboard adds “Cash collected (paid only)”: `SUM(total)` for `payment_status = 'paid'` in the same Saturday–Friday Asia/Dhaka week as gross revenue. `payment_status = 'refunded'` is excluded by definition. `EXPLAIN QUERY PLAN` uses `idx_orders_created_id` (SEARCH), so no new index/migration was added.
- Low-stock threshold is `inventory.lowStockThreshold` (default 5, 1–10,000), read from config by the dashboard and the product-page stock badge. The low-stock queries and hint use it.
- Wallet re-verify is `POST /api/admin/orders/:id/payment` with `action = 'reverify'`. Allowed transition is exactly `unpaid → paid` for bKash/Nagad orders, never cancelled/returned, and never for COD or `pending_verification` (use `verify` there). It uses the same optimistic UPDATE + one-row transition guard + `payment_reverified` event, so concurrent clicks produce one paid state and one event.
- Status-transition notes: the admin order page sends an optional textarea note with the existing status POST. The API already limited it to 500 characters; the UI adds `maxlength=500` and Astro escapes the event message on render.
- Coupon editing is a full PATCH on the existing `/:code` endpoint: type, value, min subtotal, date window, max uses, and active. The route merges the patch over the current row and re-validates percent/date rules. `max_uses` can be cleared (unlimited) but cannot be set below `used` (409 `coupon_max_uses_below_used`); the guarded UPDATE re-checks `used` atomically. A 0-row update re-reads the coupon to distinguish a concurrent delete (404) from the max-uses limit. Editing only writes `coupons`; order discounts/totals remain the stored snapshots.
- Inventory ruling (owner-approved Option 1 + guard): stock restores still skip lines whose product/variant was deleted after the order, and the delete confirmation warns about it. Deleting a product or variant is refused with 409 `product_in_active_orders` / `variant_in_active_orders` while it appears in any `pending`, `confirmed`, or `shipped` order. Both paths are race-safe: product deletion is one conditional `DELETE ... WHERE NOT EXISTS (...)`; variant removal is one conditional Drizzle delete plus the one-row `order_transition_guard` in the same batch, so a concurrent checkout line rolls the batch back. Deleting is allowed when it only appears in `delivered`, `cancelled`, or `returned` orders. The admin UI maps both codes to bn/en messages telling the owner to archive/deactivate instead.
- Turnstile failure is handled in the browser only: after the existing automatic retries, `use-turnstile` exposes an `error` status, and a widget that renders but never calls back also flips to `error` after 15 s. Checkout shows a friendly retry button plus the existing Messenger/WhatsApp/phone fallback built from the current cart (including a coupon applied only in the UI), and submit remains blocked without a token. The server-side Siteverify check is unchanged and is never bypassed.
- No schema migration is needed for 8A: settings are JSON rows and all new dashboard/delete queries use existing indexes. EXPLAIN output is covered by `tests/lib/phase8a-indexes.test.ts` and the Phase 7 index test.
- Page-body D1 round trips after 8A: dashboard 2 (storefront config + 6-statement KPI batch) + 1 auth + 1 banner check when `R2_PUBLIC_URL` is unset; settings 2 (settings row + test-image key) + 1 auth + the same conditional banner read; checkout/cart unchanged (1 settings read, then client re-price); order detail 2 + 1 auth. No GET handler writes D1.

## Phase 1–2

### Phase 1 — schema, config, seed
- Astro SSR plus a Hono API on one Worker; Tailwind CSS and Preact islands; D1 with Drizzle ORM; R2 for images. These are the stack decisions implemented by Phase 1.
- The D1 schema is maintained as a Drizzle schema plus SQL migrations with indexes.
- Configuration defaults live in `site.config.ts`; JSON rows in the D1 `settings` table are merged over them. Unknown keys are ignored and invalid rows are skipped with a warning, so one bad setting cannot take the site down.
- Money is stored as integer BDT and formatted only at the UI layer. Phone numbers are validated and normalized before storage. User-facing strings live in the `bn`/`en` i18n JSON files.
- The demo seed is local-only and covers three business types: clothing with size/colour variants, food with weight options, and electronics with spec attributes. Re-seeding replaces catalog rows but preserves orders, settings, coupons, and the blocklist.

### Phase 2 — admin auth, catalog management, R2 images
- Admin login uses `ADMIN_PASSPHRASE` with a constant-time compare and an httpOnly `SameSite=Lax` session cookie valid for 7 days.
- The session signing key is HKDF-SHA256 over `ADMIN_PASSPHRASE` plus a random per-install salt stored in the D1 `settings` table. There is no separate `SESSION_SECRET`.
- Failed logins are limited to 5 attempts per 15 minutes per IP, tracked in D1.
- The admin UI supports Bangla and English and is usable on phones.
- Images are resized in the browser to 400, 800, and 1600 px WebP at quality 0.8. The Worker validates the WebP header and a 1 MB per-file limit, then stores three objects under `products/{productId}/{uuid}-{thumb|md|full}.webp`.
- Images load from `R2_PUBLIC_URL` when set. When it is empty, the `/img/*` Worker route streams the same objects with `Cache-Control: public, max-age=31536000, immutable`.
- The admin can create categories, create and edit products with variants, and upload images.
